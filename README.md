# CommerceHub

Микросервисная e-commerce платформа с асинхронной обработкой заказов, платежей и событий.

Проект построен вокруг нескольких независимых сервисов, каждый из которых отвечает за свою бизнес-зону и имеет собственную базу данных. Для синхронного взаимодействия используется HTTP, для асинхронных операций — RabbitMQ, а для потоковой обработки событий и аналитики — Apache Kafka.

Весь проект запускается через Docker Compose одной командой.

## Основные сервисы

### API Gateway

Единая точка входа для frontend и внешних клиентов.

Отвечает за:

* маршрутизацию запросов;
* JWT-аутентификацию;
* взаимодействие с внутренними микросервисами;
* скрытие внутренней структуры системы от клиента.

Frontend работает только с Gateway и не взаимодействует с отдельными сервисами напрямую.

### Auth Service

Отвечает за регистрацию и авторизацию пользователей.

Реализовано:

* регистрация;
* авторизация;
* JWT access tokens;
* получение текущего пользователя;
* проверка авторизации;
* отдельная PostgreSQL база.

### Catalog Service

Отвечает за каталог товаров.

Реализовано:

* создание товаров;
* получение товара;
* получение списка товаров;
* взаимодействие с Order Service при создании заказа.

Сервис имеет собственную PostgreSQL базу.

### Order Service

Отвечает за работу с заказами и их жизненный цикл.

Основные задачи:

* создание заказа;
* получение информации о заказе;
* получение заказов пользователя;
* взаимодействие с Catalog Service;
* передача заказа на оплату;
* обработка результатов оплаты;
* работа с RabbitMQ.

Order Service также имеет собственную PostgreSQL базу.

### Payment Service

Отвечает за обработку платежей.

Сервис взаимодействует с Order Service через RabbitMQ и публикует события о результатах обработки платежей.

После обработки платежное событие передаётся в Kafka, где его могут независимо потреблять другие сервисы.

### Notify Service

Отдельный сервис для обработки уведомлений.

Он получает события через RabbitMQ и предназначен для дальнейшего подключения различных каналов уведомлений: email, push и других.

Выделение уведомлений в отдельный сервис позволяет не связывать отправку уведомлений с основной логикой оформления заказа.

### Analytics Service

Сервис аналитики, работающий с событиями из Kafka.

Получает события о платежах, обрабатывает их и сохраняет аналитические данные в MongoDB.

Таким образом, аналитическая часть системы не влияет непосредственно на основной процесс оформления заказа.

## Как проходит создание заказа

Упрощённый сценарий:

```text
Frontend
   │
   ▼
API Gateway
   │
   ▼
Order Service
   │
   ├──────────► Catalog Service
   │                 │
   │                 ▼
   │             PostgreSQL
   │
   ▼
RabbitMQ
   │
   ▼
Payment Service
   │
   ├──────────► PostgreSQL
   │
   └──────────► Kafka
                    │
                    ▼
              Analytics Service
                    │
                    ▼
                 MongoDB
```

Основная бизнес-логика разделена между независимыми сервисами, а длительные и второстепенные операции выполняются асинхронно.

## Взаимодействие между сервисами

В проекте используются три основных способа коммуникации.

### HTTP

Используется для операций, где ответ от другого сервиса необходим непосредственно в рамках текущего запроса.

Например:

```text
API Gateway
    │
    ├──► Auth Service
    ├──► Catalog Service
    └──► Order Service
```

### RabbitMQ

Используется для асинхронного взаимодействия между сервисами.

Например:

```text
Order Service
     │
     ▼
 RabbitMQ
     │
     ▼
Payment Service
     │
     ▼
RabbitMQ
     │
     ▼
Order Service
```

Такой подход позволяет не блокировать основной HTTP-запрос выполнением всех операций последовательно.

### Apache Kafka

Kafka используется как поток событий для аналитики.

```text
Payment Service
      │
      ▼
    Kafka
      │
      ▼
Analytics Service
      │
      ▼
   MongoDB
```

Дополнительные потребители событий могут подключаться к Kafka независимо от основной логики заказов.

## Базы данных

Каждый сервис владеет своей базой данных.

```text
Auth Service       → PostgreSQL
Catalog Service    → PostgreSQL
Order Service      → PostgreSQL
Payment Service    → PostgreSQL
Notify Service     → PostgreSQL
Analytics Service  → MongoDB
```

Сервисы не используют общие таблицы и не работают напрямую с базами друг друга.

Это позволяет сохранять независимость сервисов и изменять внутреннюю реализацию одного сервиса без необходимости менять остальные.

## Frontend

В проекте также реализован frontend на React + TypeScript.

Используемые технологии:

* React;
* TypeScript;
* Vite.

Frontend предоставляет интерфейс для:

* регистрации и авторизации;
* просмотра каталога;
* работы с корзиной;
* оформления заказа;
* просмотра заказов;
* отслеживания статуса заказа.

Все запросы frontend отправляет через API Gateway.

## Docker

Для запуска проекта не требуется поднимать сервисы вручную.

Вся инфраструктура описана в Docker Compose.

Запуск:

```bash
docker compose up --build
```

Docker Compose поднимает:

* frontend;
* Nginx;
* API Gateway;
* Auth Service;
* Catalog Service;
* Order Service;
* Payment Service;
* Notify Service;
* Analytics Service;
* PostgreSQL;
* MongoDB;
* RabbitMQ;
* Kafka.

После запуска frontend доступен через Nginx:

```text
http://localhost:8080
```

API также доступно через Gateway:

```text
http://localhost:8080/api/
```

## Docker Network

Все сервисы работают внутри общей Docker-сети.

Внутри контейнеров сервисы обращаются друг к другу по именам Docker Compose:

```text
auth-service:8000
catalog-service:8000
order-service:8000
payment-service:8000
```

Kafka внутри Docker доступна по:

```text
kafka:29092
```

RabbitMQ:

```text
rabbitmq:5672
```

API Gateway при этом не требуется публиковать напрямую наружу — внешние запросы проходят через Nginx.

## Что реализовано

В рамках проекта реализована микросервисная backend-система с:

* API Gateway;
* JWT-аутентификацией;
* отдельными сервисами для основных бизнес-доменов;
* отдельными базами данных для сервисов;
* синхронным HTTP-взаимодействием;
* асинхронным взаимодействием через RabbitMQ;

* отдельным аналитическим сервисом;
* PostgreSQL и MongoDB;
* React frontend;
* Nginx reverse proxy;
* Docker Compose;
* межсервисным взаимодействием внутри Docker network.

## Цель проекта

Основная цель проекта — получить практический опыт разработки распределённых backend-систем и работы с микросервисной архитектурой.

Вместо монолитного приложения бизнес-логика разделена на независимые сервисы, которые взаимодействуют между собой через HTTP и брокеры сообщений.

Проект позволяет на практике работать с такими концепциями, как:

* микросервисная архитектура;
* API Gateway;
* event-driven architecture;
* асинхронное взаимодействие;
* message brokers;
* database per service;
* JWT authentication;
* межсервисное взаимодействие;
* Docker containerization;
* eventual consistency;
* потоковая обработка событий.
